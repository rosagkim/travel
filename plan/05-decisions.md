# 의사결정 기록

구조를 선택한 이유와 앞으로 고려할 제약을 남기는 문서입니다.

## 001 · 기획과 구현을 한 저장소에서 관리

- 결정: 기획은 plan/, 화면은 src/에 둡니다.
- 이유: 요구사항과 구현을 같은 커밋에서 검토하고 변경 이력을 남길 수 있습니다.
- 결과: plan/의 마크다운은 문서 화면에도 공개됩니다.

## 002 · Vite와 JavaScript로 시작

- 결정: Vite + JavaScript + CSS를 사용합니다.
- 이유: 정적 호스팅에서 바로 실행할 수 있고 초기 설정이 작습니다.
- 확장: 화면과 상태가 복잡해지면 프레임워크 도입을 별도로 결정합니다.

## 003 · main과 배포 결과물 분리

- 결정: main에는 소스, github-pages에는 빌드 결과물과 배포 워크플로만 보관합니다.
- 이유: 소스와 생성된 파일의 역할을 분명히 유지합니다.
- 배포: Pages Source는 GitHub Actions입니다. main 푸시 시 검사·빌드·브랜치 갱신·공식 Pages 배포를 순서대로 실행합니다.
- 주의: GITHUB_TOKEN의 푸시는 다른 워크플로를 실행하지 않으므로, main 워크플로가 배포까지 수행합니다. 사용자가 github-pages에 직접 푸시하면 해당 브랜치의 별도 워크플로가 배포합니다.
- 초기 설정: 사용자 권한으로 빌드 브랜치를 한 번 생성합니다. 브랜치의 워크플로는 이후 자동 푸시에서 그대로 보존합니다.

## 004 · 정적 사이트의 범위

- 결정: 현재는 로그인과 데이터베이스 없이 동작합니다.
- 이유: 서비스 요구사항이 정해지기 전에는 서버 구성을 확정하지 않습니다.
- 제약: 서버 비밀키, 인증, 영구 저장이 필요하면 별도 API와 저장소가 필요합니다. 프런트엔드 환경변수는 비밀 저장소로 사용할 수 없습니다.
