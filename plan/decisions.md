# 합의 기록

사용자와 확인한 결정만 기록합니다. 제안이나 추측은 기획의 열린 질문에 둡니다. 결정을 바꿀 때는 기존 기록을 지우지 않고 새 결정에서 대체한 결정 ID와 이유를 남깁니다.

## D-001 · 서비스는 함께 기획한 뒤 구현

- 결정: 서비스의 목적과 기능은 아직 미정입니다. 합의 전까지 사이트는 빈 화면으로 유지합니다.
- 근거: 사용자 요청 — “아직 무슨 사이트를 만들지는 안 정했고 같이 기획해서 개발을 잘 할 수 있게 하자는 거야.”
- 이유: 확정하지 않은 서비스나 기획용 사이트를 임의로 만들지 않기 위해서입니다.

## D-002 · main에서 직접 자동 배포

- 결정: main 푸시 시 GitHub Actions가 검증·빌드하고 Pages에 직접 배포합니다.
- 근거: 사용자 요청 — “별도의 브랜치 없이 메인 브랜치를 기반으로 알아서 빌드되서 배포되게 해줘.”
- 결과: 별도 배포 브랜치를 사용하지 않습니다.

## D-003 · 기획은 저장소의 마크다운으로 관리

- 결정: 논의한 기획을 plan/에 저장하고, 합의·미정·진행 상황과 변경 이유를 구분합니다. 사이트에 기획 관리 화면을 만들지 않습니다.
- 근거: 사용자 요청 — “기획된 내용을 plan 폴더에 마크다운으로 정리”, “기획한 내용을 잘 저장 관리할 수 있는 시스템에 집중해서 개선해.”
- 결과: 현재 맥락은 시작 문서, 결정은 이 문서, 상세 기획은 주제별 파일에서 관리합니다. 실제 제품 기획은 아직 없습니다.

## D-004 · 방한 외국인 관광객 대상 쿠폰 앱

- 결정: 한국을 방문하는 외국인 관광객을 대상으로 한국에서 사용할 수 있는 쿠폰을 모아 제공하는 앱을 기획합니다.
- 근거: 사용자 요청 — “한국에 오는 외국인 관광객 대상으로 한국에서 사용할 수 있는 쿠폰을 모아서 제공하는 앱을 만들려고해.”
- 이유: 대상 사용자와 서비스의 핵심 방향을 이후 기획의 기준으로 삼기 위해서입니다.
- 변경 관계: D-001의 서비스 목적·기능 미정 부분을 이 방향으로 갱신합니다. 상세 범위와 사용자 흐름의 합의 전까지 사이트를 빈 화면으로 유지한다는 원칙은 유지합니다. D-003 이후 실제 제품 기획 초안을 생성했습니다.
- 상세 기획: [방한 외국인 관광객 쿠폰 앱](specs/tourist-coupons.md). 쿠폰 확보 방식, 사용 절차, 초기 범위와 제공 형태는 아직 미정입니다.

## D-005 · 한국 서비스의 웹 쿠폰 전반 수집과 탐색·안내

- 결정: 관광객 전용 여부와 관계없이 한국의 여러 서비스가 웹에서 제공하는 쿠폰 전반을 수집 대상으로 한다. 지역·업종별 탐색, 할인 혜택·유효기간·사용 조건 확인, 사용 가능한 매장 위치·쿠폰 사용 방법 안내를 제공한다.
- 근거: 사용자가 “관광객 전용 쿠폰이 아니라, 한국 어떤 서비스든 웹에서 제공하고 있는 쿠폰을 다 긁어모아서”라고 명확히 하고 위 탐색·안내 기능을 지정했다.
- 이유: 쿠폰의 발급 대상을 관광객으로 제한하지 않고, 방한 외국인 관광객이 여러 서비스의 쿠폰을 찾아 사용하도록 돕기 위해서다.
- 변경 관계: D-004의 대상 사용자는 유지하고 수집 대상과 핵심 기능을 구체화한다. 모든 웹 쿠폰을 이미 확보했거나 단일 수집 방식으로 수집 가능하다는 의미는 아니며, 초기 수집처와 구현 방식은 미정이다.
- 상세 기획: [방한 외국인 관광객 쿠폰 앱](specs/tourist-coupons.md).

## D-006 · 네이버 음식점 쿠폰 조사 결과로 초기 세팅

- 결정: 네이버에서 음식점 위주로 쿠폰을 조사하고 그 결과로 초기 세팅을 한다.
- 근거: 사용자 요청 — “네이버에서 음식점 위주로 쿠폰을 뒤져봐. 그 결과로 초기 세팅을 해”.
- 이유: 실제 쿠폰과 접근 가능한 정보에 근거해 초기 데이터 기반을 마련하기 위해서다.
- 상세 기획: [네이버 음식점 조사와 초기 데이터 세팅](specs/naver-food-bootstrap.md).
- 조사에 따른 구현 선택: 홍대·마포 공개 기획전을 첫 출처로 삼고 후보 23건을 저장한다. 개별 상세 검수 전 공개하지 않고 원본 서비스에서 발급·사용하도록 연결한다. 이는 사용자가 직접 지정한 지역·정책이 아니라 요청 범위 안에서 조사 결과를 바탕으로 선택한 초기 설정이다. 전체 수집 목표를 이 지역으로 제한하지 않는다.

## D-007 · 실제 탐색 화면 제공과 수정 시 자동 배포

- 결정: 사이트가 빈 화면이라는 사용자 지적에 따라 실제 쿠폰 탐색 화면을 제공하고, 수정마다 main에 푸시해 자동 배포한다.
- 근거: 사용자 요청 — “사이트 링크 들어가도 아무것도 안 뜨는데, 수정될 때마다 바로바로 배포 되게 해”.
- 이유: 사용자가 배포 주소에서 현재 구현 결과를 바로 확인할 수 있어야 한다.
- 변경 관계: D-001·D-004의 빈 화면 유지 방침을 대체한다. D-002의 main 기반 Pages 배포는 유지하고 연속 변경 시 최신 실행을 우선한다.
- 구현 선택: 23개 조사 후보는 ‘상세 조건 미확인’으로 구분해 탐색할 수 있게 한다. 검수 완료 전 사용 가능하다고 안내하지 않는다. D-006의 후보 비공개 방침을 명시된 미확인 후보 탐색으로 변경하며, 검수 완료 전용 필터에는 기존 엄격한 공개 가능 기준을 적용한다.
- 상세 기획: [쿠폰 탐색 화면과 변경 시 자동 배포](specs/coupon-explorer.md).

## D-008 · 서울·부산·제주로 탐색 확대

- 결정: 서울·부산·제주를 초기 서비스의 여행 목적지로 제공한다.
- 근거: 사용자 요청 — “서울, 부산, 제주 이렇게 외국인 많이 가는곳 3개 도시에 대해서 해줘”.
- 이유: 외국인 여행객이 방문할 도시를 기준으로 쿠폰을 찾아볼 수 있도록 한다.
- 변경 관계: D-006의 서울 마포 중심 초기 세팅을 확장한다. 서울 데이터는 유지하며 부산·제주의 출처가 있는 후보와 도시 필터를 추가한다. 제주는 제주시·서귀포시를 포함하는 제주도 여행 범위로 구현한다.
- 구현 선택: 서울 전용으로 보이지 않도록 화면 명칭을 Korea Perks로 변경한다. 검색 요약은 개별 쿠폰 ID 확인과 구분하며 미확인 상태를 유지한다.
- 상세 기획: [서울·부산·제주 확장](specs/three-city-expansion.md).

## D-009 · 매장명 한영 표시 통일

- 결정: 한국어 원명과 영문명을 세 도시 모두 함께 표시한다. 한국어 화면은 한국어명 우선, 영어 화면은 영문명 우선으로 한다. 출처에서 영문명을 확인하지 못하면 로마자 표기를 제공하고 공식 영문명으로 주장하지 않는다.
- 근거: 사용자가 도시별 매장명 언어 혼용을 지적했고, 앞서 설명한 통일 방식에 대해 “수정이 안됐어. 수정해”라고 실제 반영을 요청했다.
- 이유: 현장 간판·지도와 이름을 대조하고 외국인도 매장명을 읽을 수 있게 한다.
- 변경 관계: D-007·D-008에서 수집 언어에 따라 원문 이름 하나만 표시하던 구현을 대체한다. 원문 증거와 미검수 쿠폰 상태는 유지한다.
- 상세 기획: [매장명 표시 통일](specs/bilingual-merchant-names.md). [원명 확인 근거](research/merchant-names-2026-10-29.md).
